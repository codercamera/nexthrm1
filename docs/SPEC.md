# 1. เป้าหมายของระบบ
สร้างระบบ HRM สำหรับบริษัทขนาดเล็กถึงกลางที่ช่วยให้ฝ่าย HR จัดการข้อมูลพนักงาน เวลาเข้างาน การลา ค่าตอบแทน และประกาศภายในได้จากระบบเดียว โดยเน้นการใช้งานง่าย ข้อมูลอ่านได้เร็ว และติดตามรายการที่ต้องดำเนินการได้ชัดเจน
## ผู้ใช้งานหลัก
- **ผู้ดูแลระบบ / HR Admin** — จัดการข้อมูลพนักงาน สิทธิ์ การอนุมัติ และการตั้งค่าระบบ
- **เจ้าหน้าที่ HR** — ดูแลบุคลากร เวลา การลา ค่าตอบแทน เอกสาร และประกาศ
- **หัวหน้างาน** — ตรวจสอบทีมและอนุมัติคำขอ
- **พนักงาน** — ดูข้อมูลส่วนตัว ลงเวลา ส่งคำขอลา ดูสลิป และอ่านประกาศ

# 3. แนวทางการออกแบบ
- ใช้แถบเมนูด้านซ้ายที่คงตำแหน่ง เพื่อให้เปลี่ยนงานได้รวดเร็ว
- ใช้สีน้ำเงินเป็นสีหลัก สีเขียวสำหรับสถานะสำเร็จ สีส้มสำหรับสิ่งที่ต้องตรวจสอบ และสีแดงสำหรับข้อผิดพลาด
- เน้นตารางและรายการที่สแกนข้อมูลได้เร็ว แทนการใช้การ์ดจำนวนมาก
- ปุ่มหลักของแต่ละหน้าอยู่มุมขวาบนอย่างสม่ำเสมอ
- รองรับภาษาไทยและใช้ข้อความสั้นตรงความหมาย
- ข้อมูลสำคัญ เช่น เลขบัตรประชาชนและบัญชีธนาคาร ต้องปกปิดและจำกัดสิทธิ์
# 4. หน้าจอที่ออกแบบ
## 4.1 หน้าหลัก — Team Operations
![](notion-file-block://3f8cfa6a-5303-4c0f-88d7-316754bd5f32/59345677-5c63-4027-8626-877d7f396864?space_id=c11f08f5-2336-819d-815f-000329bbe038&name=hrm-dashboard.png)
**เป้าหมาย:** ให้ HR เห็นสถานะทีมและงานเร่งด่วนในหน้าเดียว
- แสดงพนักงานที่มาทำงาน ทำงานทางไกล ลางาน และมาสาย
- แสดงคำขอลาและเอกสารที่รอตรวจสอบ
- แสดงกิจกรรมและนัดหมายของฝ่าย HR
- ค้นหาและกรองตามแผนกได้
## 4.2 รายชื่อบุคลากร
![](notion-file-block://3bf92141-c0fc-4d12-a56a-752a5891b7d9/3c105079-256b-4411-9373-1601902cb5d4?space_id=c11f08f5-2336-819d-815f-000329bbe038&name=hrm-employee-directory.png)
**เป้าหมาย:** ให้ HR ค้นหาและจัดการทะเบียนพนักงานได้รวดเร็ว
- ค้นหาจากชื่อ อีเมล หรือตำแหน่ง
- กรองตามแผนกและสถานะ
- แสดงรหัส ตำแหน่ง ประเภทการจ้าง สถานะ และวันเริ่มงาน
- เพิ่มพนักงานใหม่และเปิดหน้ารายละเอียดจากแต่ละแถว
## 4.3 เพิ่มพนักงาน
![](notion-file-block://52cb0327-d69b-49a1-b2fb-ebd358743439/1212379a-aee2-43ab-8286-ec892c7d768e?space_id=c11f08f5-2336-819d-815f-000329bbe038&name=hrm-add-employee.png)
**ข้อมูลที่ต้องรองรับ**
1. **ข้อมูลส่วนตัว** — รูป คำนำหน้า ชื่อ นามสกุล ชื่อเล่น เพศ วันเกิด เลขบัตร สัญชาติ และสถานภาพ
2. **ข้อมูลติดต่อ** — อีเมลบริษัท อีเมลส่วนตัว โทรศัพท์ และที่อยู่
3. **ข้อมูลการจ้างงาน** — รหัสพนักงาน วันที่เริ่มงาน ประเภท ตำแหน่ง แผนก หัวหน้างาน สถานที่ และตารางทำงาน
4. **ค่าตอบแทน** — เงินเดือน รอบจ่าย วิธีจ่าย ธนาคาร และบัญชีรับเงิน
5. **ผู้ติดต่อฉุกเฉิน** — ชื่อ ความสัมพันธ์ และโทรศัพท์
6. **เอกสาร** — บัตรประชาชน ทะเบียนบ้าน หน้าสมุดบัญชี และสัญญาจ้าง
**พฤติกรรมสำคัญ**
- รองรับบันทึกร่าง
- ตรวจสอบช่องบังคับก่อนบันทึก
- สร้างรหัสพนักงานและบัญชีผู้ใช้งานให้สัมพันธ์กัน
- สามารถนำเงินเดือนไปใช้สร้างรอบเงินเดือนได้
### 4.3.1 ข้อมูลการจ้างงานและค่าตอบแทน
![](notion-file-block://fd15e2d3-fefe-4273-8a10-6902514222a7/614073b1-c815-4823-90ac-df5ad3976564?space_id=c11f08f5-2336-819d-815f-000329bbe038&name=hrm-add-employee-employment-compensation.png)
**ข้อมูลการจ้างงานที่ต้องรองรับ**
- รหัสพนักงานที่ระบบสร้างอัตโนมัติ
- วันที่เริ่มงาน ประเภทการจ้าง และสถานะพนักงาน
- ระยะทดลองงานและวันสิ้นสุดทดลองงาน
- ประเภทสัญญาและวันสิ้นสุดสัญญาสำหรับสัญญามีกำหนด
- ตำแหน่ง แผนก ทีม ผู้บังคับบัญชา และระดับงาน
- ศูนย์ต้นทุน สถานที่ทำงาน และรูปแบบการทำงาน
- ตารางทำงาน วันหยุดประจำสัปดาห์ และการสร้างบัญชีผู้ใช้พร้อมพนักงาน
**ข้อมูลค่าตอบแทนที่ต้องรองรับ**
- เงินเดือนพื้นฐาน ประเภทค่าจ้าง และรอบการจ่าย
- วันที่จ่ายและวันที่เริ่มมีผล
- วิธีคำนวณค่าล่วงเวลา
- รายได้ประจำหลายรายการ เช่น ค่าเดินทางและค่าโทรศัพท์
- รายการหักประจำ เช่น ประกันสังคมและภาษี
- การเข้าร่วมประกันสังคมและการหักภาษี ณ ที่จ่าย
- วิธีจ่าย ธนาคาร เลขบัญชี ชื่อบัญชี และเอกสารหน้าสมุดบัญชี
- การเลือกใช้ค่าตอบแทนเพื่อสร้างรอบเงินเดือนอัตโนมัติ
**กฎการตรวจสอบ**
1. วันสิ้นสุดทดลองงานต้องไม่น้อยกว่าวันเริ่มงาน
2. สัญญามีกำหนดต้องระบุวันสิ้นสุดสัญญา
3. เงินเดือนต้องมากกว่าศูนย์และใช้สกุลเงินบาท
4. รายได้และรายการหักต้องมีชื่อ ประเภท จำนวนเงิน และวันที่มีผล
5. เลขบัญชีต้องถูกปกปิดเมื่อแสดงผล และจำกัดสิทธิ์การเข้าถึง
6. ระบบต้องสรุปค่าใช้จ่ายต่อเดือนก่อนบันทึก
7. ข้อมูลที่ยังไม่ครบสามารถบันทึกเป็นร่างได้ แต่ยังไม่สามารถเปิดใช้งานพนักงาน
## 4.4 รายละเอียดพนักงาน
![](notion-file-block://e28ec90e-d680-4b47-96bb-fd669e0abe69/88dd5185-7598-4fc2-95cc-0b1f6aeeff86?space_id=c11f08f5-2336-819d-815f-000329bbe038&name=hrm-employee-profile.png)
**เป้าหมาย:** รวมข้อมูลสำคัญของพนักงานในหน้าเดียว
- โปรไฟล์ สถานะ ช่องทางติดต่อ และข้อมูลการจ้างงาน
- สรุปการลงเวลาวันนี้และสิทธิ์ลาคงเหลือ
- เงินเดือนและบัญชีรับเงินแบบจำกัดสิทธิ์
- ผู้ติดต่อฉุกเฉินและสถานะเอกสาร
- ประวัติการทำงานล่าสุด
- ดาวน์โหลดและแก้ไขข้อมูล
### 4.4.1 แก้ไขข้อมูลพนักงาน
![](notion-file-block://b9061c07-1dbc-4e00-bb79-7ab95eae7247/f6458e45-cb33-425e-b9e6-0b2b277b01b9?space_id=c11f08f5-2336-819d-815f-000329bbe038&name=hrm-edit-employee.png)
**เป้าหมาย:** ให้ HR แก้ไขข้อมูลได้อย่างปลอดภัย ตรวจสอบการเปลี่ยนแปลงก่อนบันทึก และรักษาประวัติย้อนหลังที่ตรวจสอบได้
**ข้อมูลที่แก้ไขได้**
- ข้อมูลส่วนตัวและช่องทางติดต่อ
- สถานะการจ้าง ประเภทการจ้าง ตำแหน่ง แผนก และผู้บังคับบัญชา
- สถานที่ รูปแบบ และตารางการทำงาน
- เงินเดือน รอบการจ่าย และบัญชีรับเงินตามสิทธิ์ของ HR
- ผู้ติดต่อฉุกเฉินและเอกสารประกอบ
**ข้อกำหนดการทำงาน**
1. โหลดข้อมูลปัจจุบันมาแสดงในฟอร์มโดยอัตโนมัติ
2. ล็อกข้อมูลสำคัญ เช่น รหัสพนักงาน อีเมลบริษัท เลขบัตรประชาชน และบัญชีธนาคาร โดยใช้ขั้นตอนขอสิทธิ์เมื่อต้องแก้ไข
3. แสดงค่าก่อนและค่าหลังเฉพาะช่องที่มีการเปลี่ยนแปลง
4. บังคับระบุ **เหตุผลในการแก้ไข** และ **วันที่มีผล**
5. เมื่อเปลี่ยนสถานะเป็น “ลาออก” ต้องระบุวันที่สิ้นสุดการจ้างและเหตุผลที่ออก
6. เมื่อเปลี่ยนเงินเดือน ต้องสร้างประวัติเงินเดือนรายการใหม่ ห้ามเขียนทับประวัติเดิม
7. รองรับการบันทึกร่างและการยกเลิกโดยเตือนเมื่อมีข้อมูลที่ยังไม่บันทึก
8. เลือกแจ้งพนักงานเกี่ยวกับการเปลี่ยนแปลงได้
9. ตรวจสอบช่องบังคับ รูปแบบข้อมูล และเอกสารก่อนอนุญาตให้บันทึก
10. บันทึก Audit Log ได้แก่ ผู้แก้ไข วันเวลา ค่าเดิม ค่าใหม่ เหตุผล และวันที่มีผล
**สิทธิ์และความปลอดภัย**
- พนักงานแก้ไขได้เฉพาะข้อมูลส่วนตัวที่กำหนด และส่งคำขอให้ HR ตรวจสอบ
- HR แก้ไขข้อมูลการจ้างงานได้ตามสิทธิ์
- ข้อมูลค่าตอบแทนและบัญชีธนาคารจำกัดเฉพาะบทบาทที่ได้รับอนุญาต
- การแก้ไขข้อมูลสำคัญควรต้องยืนยันตัวตนซ้ำหรือผ่านขั้นตอนอนุมัติ
- ทุกการเปลี่ยนแปลงต้องย้อนดูได้จากแท็บ **ประวัติการแก้ไข**
#### การแก้ไขข้อมูลการจ้างงานและค่าตอบแทน
![](notion-file-block://1170b802-f776-4b54-a269-5615824c1ae8/0c0deba4-2cfd-4fa3-ad3d-bb6f34771f92?space_id=c11f08f5-2336-819d-815f-000329bbe038&name=hrm-edit-employee-employment-compensation.png)
**ข้อมูลการจ้างงาน**
- เปลี่ยนตำแหน่ง แผนก ทีม ผู้บังคับบัญชา ระดับงาน และศูนย์ต้นทุน
- เปลี่ยนประเภทการจ้าง สถานะ สถานที่ รูปแบบ และตารางทำงาน
- การเปลี่ยนสถานะเป็น “ลาออก” ต้องระบุวันสิ้นสุดการจ้างและเหตุผลที่ออก
- การเปลี่ยนทุกครั้งต้องมีวันที่มีผล และต้องไม่เขียนทับประวัติเดิม
- ระบบต้องแสดงค่าปัจจุบันเทียบกับค่าใหม่ก่อนบันทึก
**ข้อมูลค่าตอบแทน**
- แสดงเงินเดือนปัจจุบันแบบอ่านอย่างเดียวและกรอกเงินเดือนใหม่แยกต่างหาก
- ระบุประเภทการปรับ เช่น ปรับประจำปี เลื่อนตำแหน่ง หรือแก้ไขข้อมูล
- คำนวณจำนวนและเปอร์เซ็นต์ที่เปลี่ยนแปลง
- กำหนดวันที่มีผลให้สัมพันธ์กับรอบเงินเดือน
- แก้ไขรายได้ประจำ รายการหัก และบัญชีรับเงินตามสิทธิ์
- การเปลี่ยนเงินเดือนต้องสร้างประวัติค่าตอบแทนรายการใหม่
- รองรับขั้นตอนอนุมัติค่าตอบแทนก่อนนำไปใช้จริง
- แจ้งเตือนเมื่อวันที่มีผลอยู่ในรอบเงินเดือนที่ปิดแล้ว
**การอนุมัติและ Audit**
1. ระบุเหตุผลและวันที่มีผลทุกครั้ง
2. แสดงรายการเปลี่ยนแปลงทั้งหมดก่อนกดยืนยัน
3. จำกัดการแก้ไขเงินเดือนและบัญชีรับเงินเฉพาะผู้มีสิทธิ์
4. รองรับการส่งอนุมัติและบันทึกผู้อนุมัติ
5. บันทึกค่าเดิม ค่าใหม่ ผู้แก้ไข ผู้อนุมัติ เวลา เหตุผล และแหล่งที่มา
### 4.4.2 ประวัติการแก้ไขข้อมูลพนักงาน
![](notion-file-block://8cbf43ca-32e6-4dfe-aa37-ec29eb398f2b/dc000929-2dc3-4b05-aeb8-d3d49c2addd5?space_id=c11f08f5-2336-819d-815f-000329bbe038&name=hrm-employee-audit-history.png)
**เป้าหมาย:** ให้ HR และผู้ดูแลระบบตรวจสอบประวัติการเปลี่ยนแปลงย้อนหลังได้อย่างโปร่งใส โดยข้อมูล Audit Log เป็นแบบอ่านอย่างเดียวและไม่สามารถลบหรือแก้ไขได้
**ข้อมูลที่แสดง**
- วันและเวลาที่ดำเนินการ
- หมวดข้อมูลและรายการที่เปลี่ยน
- ผู้ดำเนินการและบทบาท
- แหล่งที่มา เช่น เว็บ HRM ระบบอัตโนมัติ หรือ API
- สถานะการดำเนินการ
- ค่าเดิมและค่าใหม่
- เหตุผลในการแก้ไขและวันที่มีผล
- สถานะการแจ้งพนักงาน
- Change ID, IP Address และ Session ID แบบปกปิด
**ความสามารถ**
- กรองช่วงเวลา หมวดข้อมูล และผู้ดำเนินการ
- ค้นหารายการเปลี่ยนแปลง
- เปิดดูรายละเอียดค่าก่อน–หลัง
- ดูรายการที่เกี่ยวข้องในธุรกรรมเดียวกัน
- ส่งออกรายงานตามสิทธิ์
- แสดงรายการจากระบบอัตโนมัติแยกจากการแก้ไขโดยผู้ใช้
**ข้อกำหนดด้านความปลอดภัย**
- Audit Log ต้องเป็น Append-only
- ห้ามผู้ใช้แก้ไขหรือลบรายการย้อนหลัง
- จำกัดการเห็นข้อมูลอ่อนไหวตามบทบาท
- ปกปิด IP, Session ID และข้อมูลส่วนบุคคลที่ไม่จำเป็น
- กำหนดระยะเวลาการเก็บรักษาตามนโยบายองค์กรและกฎหมายที่เกี่ยวข้อง

## 4.7 ค่าตอบแทนและเงินเดือน
![](notion-file-block://fdd94ebd-b28d-452b-87b1-20a2e0141b60/d8d42e53-90a0-438d-b7b7-4f3343c7e021?space_id=c11f08f5-2336-819d-815f-000329bbe038&name=hrm-compensation.png)
**เป้าหมาย:** เตรียมรอบเงินเดือนและตรวจสอบข้อมูลก่อนจ่าย
- สรุปจำนวนพนักงานที่คำนวณแล้วและต้องตรวจสอบ
- แสดงเงินเดือน ค่าล่วงเวลา เบี้ยเลี้ยง รายการหัก และยอดสุทธิ
- แจ้งปัญหา เช่น ไม่มีข้อมูลลงเวลา มีวันลาที่ยังไม่ตัดค่า หรือเปลี่ยนบัญชีธนาคาร
- รองรับโครงสร้างเงินเดือน ประวัติรอบจ่าย และสลิปเงินเดือน
- สกุลเงินเริ่มต้น: บาทไทย
### 4.7.1 สร้างรอบเงินเดือน
**เป้าหมาย:** ให้เจ้าหน้าที่เงินเดือนกำหนดงวด เลือกพนักงาน ตรวจสอบองค์ประกอบการคำนวณ และแก้ไขข้อผิดพลาดก่อนสร้างรอบเงินเดือนจริง
**ขั้นตอนการทำงาน**
1. **กำหนดรอบ** — ระบุชื่อรอบ ประเภท งวดวันที่ วันตัดข้อมูล วันที่จ่าย และสกุลเงิน
2. **ตรวจสอบพนักงาน** — เลือกพนักงานที่เข้าเงื่อนไข ตรวจวันเริ่มงาน สถานะ และข้อยกเว้น
3. **คำนวณ** — รวมเงินเดือน รายได้ OT รายการหัก เวลา และการลา
4. **อนุมัติและออกสลิป** — ตรวจยอด ส่งอนุมัติ ปิดรอบ และสร้างสลิปเงินเดือน
**ข้อมูลรอบเงินเดือน**
- ชื่อรอบและประเภทรอบ เช่น รายวัน รายสัปดาห์ รายสองสัปดาห์ และรายเดือน
- วันที่เริ่ม–สิ้นสุดงวด
- วันที่ตัดข้อมูลเวลาและการลา
- วันที่จ่ายเงินเดือน
- สถานะ ฉบับร่าง กำลังตรวจสอบ รออนุมัติ อนุมัติแล้ว และปิดรอบ
- สกุลเงิน: บาทไทย
- ตัวเลือกคำนวณตามจำนวนวันที่ทำงานจริง
- ตัวเลือกรวมพนักงานที่เริ่มงานระหว่างงวด
**การเลือกพนักงาน**
- แสดงพนักงานที่เข้าเงื่อนไข รวมในรอบ และถูกยกเว้น
- ค้นหาและกรองตามแผนก ประเภทการจ้าง และสถานะ
- ตรวจสอบวันที่เริ่มงาน วันสิ้นสุดการจ้าง และสถานะบัญชีรับเงิน
- รองรับข้อยกเว้นรายบุคคล พร้อมบันทึกเหตุผล
- พนักงานที่ออกก่อนงวดหรือถูกพักการจ่ายต้องไม่ถูกรวมโดยอัตโนมัติ
**องค์ประกอบการคำนวณ**
- **รายได้:** เงินเดือนพื้นฐาน ค่าล่วงเวลา เบี้ยเลี้ยง รายได้ประจำ โบนัส และรายได้อื่น
- **รายการหัก:** ประกันสังคม ภาษี ขาดงาน ลาโดยไม่ได้รับค่าจ้าง รายการหักประจำ และรายการหักอื่น
- **ข้อมูลเวลา:** วันทำงาน มาสาย ขาดงาน OT และการลาที่อนุมัติแล้ว
- รองรับสูตรคำนวณที่กำหนดได้และมีเวอร์ชัน
- แสดงแหล่งที่มาของแต่ละยอดเพื่อให้ตรวจสอบย้อนหลังได้
**การตรวจสอบก่อนสร้างรอบ**
- ข้อมูลเวลาไม่ครบ
- คำขอลาที่ยังรออนุมัติ
- บัญชีธนาคารถูกเปลี่ยนหรือยังไม่ยืนยัน
- เงินเดือนหรือโครงสร้างค่าตอบแทนไม่มีวันที่มีผล
- ยอดสุทธิติดลบ
- ข้อมูลภาษีหรือประกันสังคมไม่ครบ
- พนักงานซ้ำหรืออยู่ในรอบอื่นที่ทับซ้อนกัน
**การอนุมัติและความปลอดภัย**
- ระบุผู้อนุมัติรอบเงินเดือน
- แยกผู้จัดทำ ผู้ตรวจสอบ และผู้อนุมัติ
- ข้อมูลค่าตอบแทนแสดงเฉพาะบทบาทที่ได้รับสิทธิ์
- การคำนวณซ้ำต้องสร้างเวอร์ชันใหม่และเก็บผลเดิม
- การปิดรอบแล้วห้ามแก้ไขโดยตรง ต้องเปิดรอบใหม่หรือสร้างรายการปรับปรุง
- บันทึก Audit Log ของการสร้าง คำนวณ แก้ไข อนุมัติ ปิดรอบ และออกสลิป
**สรุปที่ต้องแสดงแบบทันที**
- จำนวนพนักงานในรอบ
- ยอดเงินเดือนพื้นฐาน
- รายได้เพิ่มเติม
- รายการหัก
- ยอดสุทธิโดยประมาณ
- วันที่จ่าย
- จำนวนข้อผิดพลาดและคำเตือนที่ต้องแก้ไข
![](notion-file-block://1a08509d-33e1-475f-8c23-5a82a61dc832/089ec8fc-6e36-41ac-a64f-73f4f7472245?space_id=c11f08f5-2336-819d-815f-000329bbe038&name=hrm-create-payroll-cycle.png)

#### รายการแจ้งเตือนที่ต้องตรวจสอบ
- ข้อมูลเวลาทำงานหรือ OT ไม่ครบ
- เงินเดือนสุทธิเปลี่ยนแปลงเกินเกณฑ์ เช่น 10%
- บัญชีธนาคารมีการเปลี่ยนแปลง
- ยอดสุทธิติดลบหรือเป็นศูนย์
- คำขอลาหรือรายการปรับปรุงยังรออนุมัติ
- ข้อมูลภาษีหรือประกันสังคมไม่ครบ
- รายการนำเข้าซ้ำหรือยอดผิดจากสูตร
#### แผงรายละเอียดพนักงาน
เมื่อเลือกรายการ ให้แสดงที่มาของรายได้และรายการหักทุกประเภท พร้อมสูตร จำนวน หน่วย อัตรา และยอดเงิน รวมถึงเปรียบเทียบกับงวดก่อนหน้าและเหตุผลของความเปลี่ยนแปลง
#### การค้นหาและควบคุม
- ค้นหาด้วยชื่อหรือรหัสพนักงาน
- กรองตามแผนก สถานะ และประเภทข้อผิดพลาด
- แสดงเฉพาะรายการที่มีการเปลี่ยนแปลง
- ดูเวอร์ชันการคำนวณและเวลาที่คำนวณล่าสุด
- คำนวณใหม่หลังแก้ไขข้อมูลต้นทาง
- ส่งออกข้อมูลสำหรับตรวจสอบ โดยควบคุมสิทธิ์การเข้าถึง
#### กฎการอนุมัติ
1. ข้อผิดพลาดระดับปิดกั้นต้องถูกแก้ไขก่อนส่งอนุมัติ
2. ผู้จัดทำต้องยืนยันว่าได้ตรวจสอบข้อมูลครบถ้วน
3. การคำนวณใหม่ต้องสร้างเวอร์ชันใหม่และเก็บเวอร์ชันเดิม
4. การแก้ไขยอดด้วยตนเองต้องบันทึกเหตุผลและผู้แก้ไข
5. แยกบทบาทผู้จัดทำ ผู้ตรวจสอบ และผู้อนุมัติ
6. บันทึก Audit Log สำหรับการคำนวณ แก้ไข ส่งอนุมัติ อนุมัติ และส่งออก
7. เมื่ออนุมัติหรือปิดรอบแล้ว ห้ามแก้ไขโดยตรง ต้องเปิดรอบแก้ไขตามสิทธิ์
#### ความปลอดภัย
- จำกัดการเห็นข้อมูลเงินเดือนตามบทบาทและขอบเขตองค์กร
- ปกปิดเลขบัญชีธนาคารและข้อมูลส่วนบุคคลที่ไม่จำเป็น
- บันทึกประวัติการดาวน์โหลดและส่งออกข้อมูล
- รองรับการอนุมัติแบบสองชั้นสำหรับยอดที่เกินเกณฑ์

# 5. ขั้นตอนการทำงานหลัก
## เพิ่มพนักงาน
1. HR เปิดเมนูบุคลากรและเลือก **เพิ่มพนักงาน**
2. กรอกข้อมูลและแนบเอกสาร

5. ติดตามจำนวนผู้เปิดอ่านและกิจกรรมรายบุคคล

# 8. งานออกแบบลำดับถัดไป — รายละเอียดฉบับสมบูรณ์
> **สถานะ:** ออกแบบข้อกำหนดครบแล้วและพร้อมส่งต่อให้ทีมพัฒนา
> เครื่องหมาย `[x]` หมายถึง User flow, ข้อมูล, สิทธิ์, สถานะหน้าจอ และเกณฑ์ตรวจรับได้รับการกำหนดครบถ้วนแล้ว
## 8.1 แบบฟอร์มสร้างและแก้ไขประกาศ
- [x] ออกแบบครบและพร้อมพัฒนา
**ผู้ใช้งาน:** Admin และ HR ที่ได้รับสิทธิ์สร้างประกาศ
**โครงสร้างหน้าจอ**
1. Header แสดงชื่อหน้า สถานะปัจจุบัน ปุ่มบันทึกร่าง ดูตัวอย่าง และเผยแพร่
2. ข้อมูลหลักประกอบด้วยหัวข้อ เนื้อหา รูปหน้าปก ระดับความสำคัญ และไฟล์แนบ
3. กลุ่มผู้รับเลือกได้จากทุกคน สาขา แผนก บทบาท หรือรายบุคคล
4. การเผยแพร่เลือกได้ระหว่างเผยแพร่ทันทีหรือตั้งวันและเวลา
5. กำหนดวันหมดอายุและตัวเลือกให้ผู้รับกดยืนยันการรับทราบ
6. Preview แสดงตัวอย่างบน Desktop และ Mobile ก่อนเผยแพร่
7. หลังเผยแพร่แสดงจำนวนผู้รับ ผู้เปิดอ่าน จำนวนการเปิดทั้งหมด และรายชื่อผู้ที่ยังไม่อ่าน
**สถานะประกาศ**
`DRAFT → SCHEDULED → PUBLISHED → ARCHIVED`
สามารถเปลี่ยนเป็น `CANCELLED` ก่อนหรือหลังเผยแพร่ตามสิทธิ์
**กฎการทำงาน**
- ต้องมีหัวข้อ เนื้อหา และกลุ่มผู้รับอย่างน้อยหนึ่งกลุ่ม
- เวลาตั้งเผยแพร่ต้องมากกว่าเวลาปัจจุบัน
- ผู้สร้างประกาศไม่ต้องได้รับ Notification จากประกาศของตนเอง
- เมื่อผู้ใช้เปิดประกาศ ให้ลด Badge เฉพาะ Notification รายการนั้น
- Admin ดูผู้เปิดอ่านและจำนวนครั้งได้จาก Query แบบรวม ไม่เรียก API แยกทีละประกาศ
- การแก้ไขประกาศที่เผยแพร่แล้วต้องเก็บ Revision และ Audit Log
**ข้อมูลหลักที่ใช้**
`announcements`, `announcement_targets`, `announcement_user_activity`, `notifications`, `file_attachments`, `audit_logs`
**เกณฑ์ตรวจรับ**
- บันทึกร่าง ตั้งเวลา เผยแพร่ ยกเลิก และเก็บถาวรได้
- เลือกกลุ่มเป้าหมายหลายประเภทได้โดยไม่ส่งซ้ำ
- Preview ใกล้เคียงหน้าจอที่ผู้รับเห็นจริง
- รายงานการเปิดอ่านถูกต้องทั้ง Unique viewer และจำนวนครั้งรวม
- ผู้ไม่มีสิทธิ์ไม่สามารถสร้าง แก้ไข หรือดูรายชื่อผู้เปิดอ่านได้
## 8.2 หน้าปฏิทินการลา
- [x] ออกแบบครบและพร้อมพัฒนา
**ผู้ใช้งาน:** พนักงาน หัวหน้างาน HR และ Admin
**โครงสร้างหน้าจอ**
1. มุมมองรายเดือน รายสัปดาห์ และรายการ
2. แถบสรุปจำนวนคนลาในวันนี้ คำขอรออนุมัติ และความเสี่ยงกำลังคนไม่พอ
3. ตัวกรองสาขา แผนก ประเภทลา สถานะ และพนักงาน
4. สีแยกประเภทและสถานะลา พร้อม Legend ที่อ่านได้ใน Light/Dark mode
5. คลิกวันที่เพื่อสร้างคำขอลา และคลิกรายการเพื่อเปิดรายละเอียด
6. Drawer รายละเอียดแสดงช่วงเวลา จำนวนวัน/ชั่วโมง เหตุผล เอกสาร และ Approval timeline
7. พนักงานเห็นยอดลาคงเหลือของตนเอง ส่วนหัวหน้างานเห็นเฉพาะสมาชิกในทีม
**กฎความเป็นส่วนตัว**
- พนักงานทั่วไปเห็นว่าบุคคลใดไม่อยู่ แต่ไม่เห็นเหตุผลหรือเอกสารของผู้อื่น
- หัวหน้างานเห็นรายละเอียดเฉพาะทีมที่ตนดูแล
- HR/Admin เห็นรายละเอียดตามสิทธิ์องค์กร
- ประเภทลาที่อ่อนไหวสามารถแสดงเป็น “ลา” โดยไม่ระบุประเภท
**การตรวจสอบก่อนส่งคำขอ**
- ตรวจวันที่ซ้อน วันหยุด ตารางงาน และยอดคงเหลือ
- แจ้งเตือนเมื่อมีคนลาในทีมเกินเกณฑ์
- ประเภทลาที่กำหนดต้องแนบเอกสาร
- รองรับลาเต็มวัน ครึ่งวัน และรายชั่วโมง
- คำขอที่อนุมัติแล้วต้องเชื่อม Attendance และ Payroll
**ข้อมูลหลักที่ใช้**
`leave_types`, `leave_policies`, `employee_leave_balances`, `leave_requests`, `leave_request_days`, `leave_approvals`, `work_schedules`
**เกณฑ์ตรวจรับ**
- ปฏิทินและรายการแสดงข้อมูลตรงกัน
- Filter ทำงานร่วมกันและคงค่าเมื่อย้อนกลับจากหน้ารายละเอียด
- การอนุมัติหรือปฏิเสธปรับ Timeline และยอดคงเหลือถูกต้อง
- ข้อมูลส่วนตัวไม่รั่วไหลข้ามทีมและขอบเขตสิทธิ์
## 8.3 หน้ารายละเอียดรอบเงินเดือนและสลิป
- [x] ออกแบบครบและพร้อมพัฒนา
**ผู้ใช้งาน:** Payroll officer, HR reviewer, ผู้อนุมัติ และพนักงานเจ้าของสลิป
**หน้ารายละเอียดรอบเงินเดือน**
1. Header แสดงชื่อรอบ ช่วงวันที่ วันจ่าย สถานะ Version และผู้รับผิดชอบ
2. Stepper แสดง กำหนดรอบ → ตรวจพนักงาน → คำนวณ → ตรวจสอบ → อนุมัติ → ออกสลิป
3. Summary cards แสดงจำนวนพนักงาน รายได้รวม รายการหัก ภาษี ประกันสังคม และยอดสุทธิ
4. ตารางรายพนักงานแสดงเงินเดือน รายได้เพิ่ม OT รายการหัก ภาษี ประกันสังคม สุทธิ ส่วนต่าง และสถานะ
5. แผง Issues แยก Blocking error และ Warning
6. Drawer พนักงานแสดงรายละเอียดรายการ สูตร ที่มาของข้อมูล และเปรียบเทียบงวดก่อน
7. Approval timeline แสดงผู้จัดทำ ผู้ตรวจสอบ ผู้อนุมัติ ความเห็น และเวลา
8. Version history ให้เปรียบเทียบผลคำนวณแต่ละ Version โดยไม่ลบผลเดิม
**หน้าสลิปเงินเดือน**
- แสดงข้อมูลองค์กร พนักงาน งวด วันจ่าย รายได้ รายการหัก และยอดสุทธิ
- แสดง YTD เมื่อมีข้อมูลครบ
- ดาวน์โหลด PDF ได้เฉพาะเจ้าของข้อมูลและผู้มีสิทธิ์
- ปกปิดเลขบัญชีและข้อมูลส่วนบุคคลที่ไม่จำเป็น
- บันทึกครั้งแรก ครั้งล่าสุด และจำนวนครั้งที่เปิดดู
- สลิปที่ถูกยกเลิกต้องเปิดไม่ได้และแสดงเหตุผลแก่ผู้มีสิทธิ์
**กฎการอนุมัติ**
- ห้ามส่งอนุมัติเมื่อมี Blocking error
- การคำนวณใหม่สร้าง Version ใหม่เสมอ
- Manual adjustment ต้องระบุเหตุผล
- ผู้จัดทำ ผู้ตรวจสอบ และผู้อนุมัติต้องแยกบทบาทตามนโยบาย
- รอบที่อนุมัติ จ่าย หรือปิดแล้วห้ามแก้ไขโดยตรง
**ข้อมูลหลักที่ใช้**
`payroll_cycles`, `payroll_cycle_employees`, `payroll_calculation_runs`, `payroll_results`, `payroll_result_items`, `payroll_adjustments`, `payroll_approvals`, `payslips`
**เกณฑ์ตรวจรับ**
- ยอดรวมบน Summary ตรงกับผลรวมรายการพนักงาน
- เปลี่ยน Version แล้วข้อมูล ตาราง Issues และยอดรวมเปลี่ยนตรงกัน
- ผู้ไม่มีสิทธิ์ไม่สามารถเห็นเงินเดือนหรือดาวน์โหลดสลิปของผู้อื่น
- Audit Log ครอบคลุมคำนวณใหม่ ปรับยอด ส่งอนุมัติ อนุมัติ จ่าย ปิดรอบ และดาวน์โหลด
## 8.4 หน้าจอพนักงานสำหรับ Self-service
- [x] ออกแบบครบและพร้อมพัฒนา
**ผู้ใช้งาน:** พนักงานที่เข้าสู่ระบบด้วยบัญชีของตนเอง
**เมนูหลัก**
1. **หน้าหลักของฉัน** — สรุปสถานะวันนี้ วันลาคงเหลือ คำขอรออนุมัติ ประกาศล่าสุด และสลิปล่าสุด
2. **ข้อมูลส่วนตัว** — แสดงเป็น Form รายละเอียดพนักงาน ไม่ใช้หน้ารายการหรือช่องค้นหาพนักงาน
3. **ข้อมูลการจ้างงาน** — แผนก ตำแหน่ง หัวหน้า ประเภทการจ้าง วันที่เริ่มงาน และสถานะ แบบอ่านอย่างเดียว
4. **ประวัติการทำงาน** — แสดงถัดจากรายละเอียดพนักงานโดยไม่ต้องกดปุ่มเปิด Dialog
5. **เวลาและการลา** — ลงเวลา ดูประวัติ ส่งคำขอลา และดู Approval timeline
6. **ค่าตอบแทนและสลิป** — ดูค่าตอบแทนปัจจุบันตามสิทธิ์และสลิปของตนเอง
7. **ประกาศและการแจ้งเตือน** — อ่านประกาศและจัดการ Notification ของตนเอง
**สิทธิ์แก้ไขข้อมูล**
- แก้ไขเบอร์โทร อีเมลส่วนตัว ที่อยู่ และผู้ติดต่อฉุกเฉินได้
- การเปลี่ยนชื่อ เลขประจำตัว บัญชีธนาคาร หรือข้อมูลภาษีต้องส่งคำขอให้ HR ตรวจสอบ
- พนักงานเพิ่มประวัติการทำงานของตนเองได้ แต่แก้ไขหรือลบรายการที่ส่งแล้วไม่ได้
- ข้อมูลการจ้างงาน ตำแหน่ง แผนก เงินเดือน และสถานะเป็นข้อมูลอ่านอย่างเดียว
- ทุกการเปลี่ยนแปลงต้องบันทึกผู้ดำเนินการ เวลา และค่าก่อน/หลัง
**สถานะหน้าจอ**
- Loading skeleton
- Empty state พร้อมปุ่มดำเนินการที่เกี่ยวข้อง
- Validation error ระดับช่องกรอก
- Permission denied ที่อธิบายว่าต้องติดต่อใคร
- Pending review สำหรับข้อมูลที่รอ HR ตรวจสอบ
- Success state พร้อมเลขอ้างอิง
**เกณฑ์ตรวจรับ**
- พนักงานเข้าถึงได้เฉพาะข้อมูลตนเอง
- Profile แสดงเป็น Form และประวัติการทำงานอยู่ในหน้าเดียวกัน
- การแก้ไขข้อมูลสำคัญไม่เปลี่ยนข้อมูลจริงก่อน HR อนุมัติ
- หน้าใช้งานได้ครบทั้ง Desktop, Tablet และ Mobile
## 8.5 User Management และการกำหนดสิทธิ์
- [x] ออกแบบครบและพร้อมพัฒนา
**ผู้ใช้งาน:** Admin และผู้ดูแลสิทธิ์ที่ได้รับมอบหมาย
**หน้ารายชื่อผู้ใช้**
- ค้นหาด้วยชื่อ Email หรือรหัสพนักงาน
- กรองตามสถานะ Role สาขา แผนก และวันที่เข้าใช้ล่าสุด
- แสดงบัญชีที่ยังไม่เชื่อมพนักงานหรือพนักงานที่ยังไม่มีบัญชี
- Bulk action สำหรับเชิญผู้ใช้ เปิด/ปิดใช้งาน และกำหนด Role
- ห้ามผู้ดูแลปิดใช้งานบัญชีของตนเองหากจะทำให้ระบบไม่มี Admin เหลือ
**หน้ารายละเอียดผู้ใช้**
- ข้อมูลบัญชี พนักงานที่เชื่อม สถานะ และประวัติการเข้าใช้
- ส่งคำเชิญใหม่ รีเซ็ตรหัสผ่าน ปลดล็อก ระงับ หรือปิดบัญชี
- กำหนด Role ได้หลายรายการ
- กำหนด Scope เป็น Organization, Branch, Department หรือ Self
- แสดง Effective permissions ที่รวมจากทุก Role และ Scope
- แสดงประวัติการเปลี่ยนสิทธิ์โดยไม่ให้แก้ไขย้อนหลัง
**หน้าจัดการ Role**
- สร้าง Role แบบกำหนดเองจาก Permission matrix
- แยกสิทธิ์ View, Create, Edit, Delete, Approve, Export และ Admin
- System role แก้ Code หรือลบไม่ได้
- แสดงจำนวนผู้ใช้ที่ได้รับ Role ก่อนอนุญาตให้ลบ
- Preview ผลกระทบก่อนบันทึกการเปลี่ยน Permission
**ข้อมูลหลักที่ใช้**
`users`, `employees`, `roles`, `permissions`, `user_roles`, `role_permissions`, `audit_logs`
**เกณฑ์ตรวจรับ**
- สิทธิ์ที่แสดงใน UI ตรงกับสิทธิ์ที่ Backend ตรวจจริง
- การเปลี่ยน Role มีผลต่อ Session ตามนโยบายที่กำหนด
- ผู้ใช้ไม่สามารถเพิ่มสิทธิ์สูงกว่าสิทธิ์ที่ตนเองมี
- ทุกการเชิญ ระงับ ปลดล็อก และเปลี่ยนสิทธิ์มี Audit Log
## 8.6 Audit Log และประวัติการเปลี่ยนแปลง
- [x] ออกแบบครบและพร้อมพัฒนา
**ผู้ใช้งาน:** Admin, Auditor และ HR ตามขอบเขตสิทธิ์
**โครงสร้างหน้าจอ**
1. Summary แสดงจำนวนเหตุการณ์วันนี้ การเปลี่ยนข้อมูลอ่อนไหว การส่งออก และเหตุการณ์ผิดปกติ
2. Filter ตามช่วงเวลา ผู้ดำเนินการ Module, Action, Object, พนักงาน และ Request ID
3. ตารางแสดงเวลา ผู้ดำเนินการ การกระทำ รายการที่ได้รับผล และเหตุผล
4. Detail drawer แสดง Before/After diff แบบเน้นช่องที่เปลี่ยน
5. เชื่อมไปยังพนักงาน คำขอลา Payroll หรือประกาศต้นทางเมื่อผู้ใช้มีสิทธิ์
6. Export ต้องเลือกเหตุผลและบันทึก Audit Log ของการ Export อีกชั้นหนึ่ง
**ประเภทเหตุการณ์ขั้นต่ำ**
- Login, Login failed, Lock, Unlock และเปลี่ยนสิทธิ์
- เพิ่มและแก้ไขพนักงาน การจ้างงาน เงินเดือน บัญชีธนาคาร และเอกสาร
- แก้ไข Attendance อนุมัติ OT และการลา
- สร้าง คำนวณใหม่ ปรับยอด อนุมัติ จ่าย และปิด Payroll
- สร้าง แก้ไข เผยแพร่ ยกเลิกประกาศ และดูรายงานผู้เปิดอ่าน
- ดาวน์โหลดหรือส่งออกข้อมูลอ่อนไหว
**กฎความปลอดภัย**
- Audit Log แก้ไขและลบผ่านหน้าจอไม่ได้
- Before/After ต้องปกปิด Password, Token, เลขบัญชีเต็ม และข้อมูลลับ
- การอ่าน Audit Log ต้องถูกตรวจสิทธิ์และบันทึกกิจกรรม
- Retention period กำหนดโดยนโยบายองค์กร
- Request ID ใช้เชื่อมเหตุการณ์หลายรายการที่เกิดจากคำสั่งเดียวกัน
**ข้อมูลหลักที่ใช้**
`audit_logs` และข้อมูลอ้างอิงจากทุกโมดูล
**เกณฑ์ตรวจรับ**
- ค้นหาเหตุการณ์จาก User, Employee, Object ID และ Request ID ได้
- Diff แสดงค่าก่อนและหลังถูกต้อง
- ไม่มีคำสั่ง Update/Delete Audit Log จาก Application role
- การ Export ต้องมีสิทธิ์ เหตุผล และประวัติย้อนหลัง

## 8.8 มาตรฐานร่วมของทุกหน้าจอ
- [x] กำหนดครบและพร้อมพัฒนา
**ภาษาและรูปแบบ**
- รองรับภาษาไทยและอังกฤษ
- วันที่แสดงตาม Locale แต่จัดเก็บเป็น ISO 8601
- จำนวนเงินแสดงเป็นบาทไทยพร้อมทศนิยมสองตำแหน่ง
- รองรับ Light mode และ Dark mode
- ใช้คำเรียก สถานะ สี และ Icon ให้สอดคล้องกันทั้งระบบ
**สถานะมาตรฐาน**
- Loading: Skeleton หรือ Progress ที่ไม่ทำให้ Layout กระโดด
- Empty: อธิบายเหตุผลและเสนอการทำงานถัดไป
- Error: แสดงข้อความที่ผู้ใช้แก้ไขได้และมี Retry เมื่อเหมาะสม
- Validation: แสดงใกล้ช่องกรอกและเลื่อนไปยังข้อผิดพลาดแรก
- Success: ยืนยันผลพร้อมเลขอ้างอิงหรือทางลัดไปยังรายการ
- Unsaved changes: เตือนก่อนออกจากหน้า
- Permission denied: ไม่เปิดเผยข้อมูลที่ไม่มีสิทธิ์และบอกช่องทางติดต่อ
**Accessibility**
- ใช้งานด้วย Keyboard ได้
- Focus state มองเห็นชัด
- Form มี Label และ Error ที่ Screen reader อ่านได้
- สีไม่เป็นวิธีเดียวที่ใช้สื่อสถานะ
- Dialog ต้องกัก Focus และคืน Focus เมื่อปิด
- ตารางสำคัญมี Header และคำอธิบายที่เหมาะสม

- Employee number, เงินเดือน, วันที่เริ่มงาน, แผนก, ตำแหน่ง และหัวหน้าเป็นข้อมูลรายบริษัท
- รองรับ Transfer, Secondment และ Dual employment
- การย้ายบริษัทต้องสร้าง Employee record ปลายทางใหม่ ไม่เปลี่ยน Company ID ของประวัติเดิม
- ประวัติ Payroll และการลาของบริษัทต้นทางต้องคงเดิม
- Self-service แสดงรายการ “การจ้างงานของฉัน” ให้เลือกบริษัทที่ต้องการดู
**Payroll และการเงิน**
- Payroll cycle หนึ่งรอบอยู่ภายใต้บริษัทเดียว
- ห้ามรวมพนักงานต่างบริษัทในรอบเดียว แม้อยู่ใน Tenant เดียวกัน
- เลขสลิป บัญชีจ่าย ภาษี ประกันสังคม และ Approval workflow แยกตามบริษัท
- Tenant Admin ดูรายงานรวมได้เฉพาะเมื่อมีสิทธิ์ในทุกบริษัทที่เลือก
- รายงานรวมต้องแสดง Company column และรองรับ Group by Company
- การ Export หลายบริษัทต้องบันทึกรายชื่อบริษัทใน Filter snapshot
**ประกาศและ Notification**
- ประกาศระดับ Tenant ส่งถึงทุกบริษัทที่ผู้สร้างมีสิทธิ์
- ประกาศระดับ Company ส่งเฉพาะบริษัทที่เลือก
- Target สามารถจำกัด Branch, Department, Role หรือ User ภายในบริษัท
- Activity และจำนวนผู้เปิดอ่านต้องแยกบริษัทเพื่อรายงานได้ถูกต้อง
- Notification ต้องเก็บทั้ง Tenant และ Company context
**Audit และการแยกข้อมูล**
- ทุกธุรกรรมต้องมี `tenant_id`
- ข้อมูลระดับบริษัทต้องมี `organization_id`
- Audit Log ต้องบันทึก Tenant, Company, User, Object และ Request ID
- Query ทุกโมดูลต้องกรอง Tenant ก่อน แล้วจึงกรอง Company ตามสิทธิ์
- ห้ามรับ `organization_id` จาก Client แล้วเชื่อถือทันที ต้องตรวจผ่าน `user_company_access`
- Cache key, Background job, File path และ Export ต้องรวม Tenant/Company ID
- Unique constraint ของเลขพนักงาน รหัสแผนก รอบ Payroll และเลขสลิปต้องแยกต่อบริษัท
**เกณฑ์ตรวจรับ**
- ผู้ใช้สลับบริษัทได้โดยไม่ต้อง Login ใหม่
- เมนูและข้อมูลเปลี่ยนตามสิทธิ์ของบริษัทปัจจุบันทันที
- ไม่สามารถเปิด URL หรือ API ของบริษัทที่ไม่มีสิทธิ์
- บุคคลเดียวมีการจ้างในหลายบริษัทได้โดยข้อมูล Payroll ไม่ปะปน
- การย้ายบริษัทไม่เปลี่ยนหรือลบประวัติของบริษัทเดิม
- Dashboard และรายงานรวมแสดงเฉพาะบริษัทที่ผู้ใช้มีสิทธิ์
- Audit Log ระบุบริษัทต้นทางของทุกเหตุการณ์ได้
- Automated test ต้องทดสอบ Cross-company data leakage เป็นกรณีบังคับ

- เมื่อเผยแพร่ ให้สร้าง `announcement_user_activity` สำหรับผู้รับทั้งหมด
- เมื่อผู้ใช้เปิดประกาศ ให้เพิ่ม `view_count` และอัปเดต `last_viewed_at`
- หน้า Admin ดึง Activity ของหลายประกาศด้วย Query เดียวแบบ JOIN/GROUP BY ไม่เรียก API แยกรายประกาศ
- ผู้สร้างประกาศไม่ควรได้รับ Notification ของประกาศที่ตนเองสร้าง
- Badge แจ้งเตือนลดลงเฉพาะเมื่อผู้ใช้เปิดรายการนั้นจริง
ตัวอย่าง Query สำหรับรายงานการเปิดอ่านหลายประกาศ:
```sql
SELECT
  a.id,
  a.title,
  COUNT(aua.user_id) AS delivered_count,
  SUM(CASE WHEN aua.view_count > 0 THEN 1 ELSE 0 END) AS unique_viewer_count,
  SUM(aua.view_count) AS total_view_count
FROM announcements a
LEFT JOIN announcement_user_activity aua
  ON aua.announcement_id = a.id
WHERE a.organization_id = ?
GROUP BY a.id, a.title
ORDER BY a.published_at DESC;
```

## 9.11 ความสัมพันธ์หลักของระบบ
- Organization 1:N Branch, Department, Position, Job Level, User และ Employee
- User 0..1:1 Employee
- Employee N:1 Department, Position, Job Level และ Manager
- Employee 1:N Employment History และ Compensation History
- Employee 1:N Attendance, OT, Leave Request และ Payroll Result
- Payroll Cycle 1:N Calculation Run และ Calculation Run 1:N Payroll Result
- Payroll Result 1:N Result Item และ 1:1 Payslip
- Announcement N:M User ผ่าน Announcement Target และ Announcement User Activity
- ทุกโมดูลส่งเหตุการณ์สำคัญเข้าสู่ Audit Log
## 9.12 Constraint ที่ต้องตรวจใน Application Service
SQLite Constraint ไม่สามารถครอบคลุมกฎธุรกิจบางชนิดได้ทั้งหมด จึงต้องตรวจเพิ่มเติมภายใน Transaction:
- ช่วงวันที่ของ Employment, Compensation, Schedule และ Bank Account ต้องไม่ซ้อนกัน
- พนักงานต้องไม่รายงานตรงหรือทางอ้อมให้ตนเอง
- วันลาต้องไม่ซ้อนกับคำขอที่อนุมัติหรือรออนุมัติ
- Payroll รอบเดียวกันต้องไม่ครอบคลุมพนักงานและช่วงเวลาซ้ำโดยไม่ได้รับอนุญาต
- บัญชีธนาคารหลักต้องผ่านการยืนยันก่อนจ่ายเงินจริง
- ห้ามแก้ข้อมูลที่เป็น Snapshot ของ Payroll เวอร์ชันที่อนุมัติแล้ว
- การลบข้อมูลทางการเงินและ Audit Log ต้องถูกปฏิเสธ ใช้สถานะหรือรายการกลับรายการแทน
- ทุกคำสั่งที่เปลี่ยนหลายตารางต้องทำใน Transaction เดียว
## 9.13 Index และ Query สำคัญ
Schema ได้เตรียม Index สำหรับ:
- รายชื่อพนักงานตามองค์กร สถานะ แผนก และหัวหน้า
- ประวัติการทำงานและค่าตอบแทนเรียงตามวันที่มีผล
- Attendance ตามวันที่และสถานะ
- Leave ตามพนักงาน ช่วงเวลา และสถานะ
- Payroll ตามงวด สถานะ และรายการที่ต้องตรวจสอบ
- ประกาศล่าสุดและ Activity แบบรวมหลายประกาศ
- Notification ที่ยังไม่อ่าน
- Audit Log ตาม Object, ผู้กระทำ และพนักงาน
เมื่อข้อมูลมีขนาดใหญ่ ควรตรวจ Query plan ด้วย `EXPLAIN QUERY PLAN` ก่อนเพิ่ม Index ใหม่ เพื่อไม่ให้การเขียนข้อมูลช้าลงโดยไม่จำเป็น

### 9.19.3 หลักการข้อมูลบุคคลและการจ้างงาน
`people` เก็บตัวตนร่วมของบุคคลภายใน Tenant ส่วน `employees` เก็บสัญญาจ้างและข้อมูลการทำงานของแต่ละบริษัท
ตัวอย่าง:
- บุคคล A ทำงานบริษัท X และบริษัท Y
- มี `people` 1 รายการ
- มี `employees` 2 รายการ โดยแต่ละรายการมี Employee number, เงินเดือน, แผนก และวันเริ่มงานของตนเอง
- User เดียวเชื่อมสิทธิ์ทั้งสองบริษัทผ่าน `user_company_access`
- Payroll และสลิปอ้าง Employee ID ของบริษัทนั้นโดยตรง
**กฎห้ามทำ**
- ห้ามย้ายพนักงานด้วยการเปลี่ยน `employees.organization_id`
- ห้ามใช้ Compensation history ของบริษัทหนึ่งคำนวณ Payroll อีกบริษัท
- ห้ามรวม Bank account, Tax profile หรือ Social security profile ข้าม Employee record โดยอัตโนมัติ
- ห้ามรวม Leave balance ข้ามบริษัท เว้นแต่มีนโยบายและกระบวนการโอนสิทธิ์ที่ชัดเจน
### 9.19.4 การย้ายและทำงานข้ามบริษัท
`intercompany_employee_transfers` รองรับ:
- `TRANSFER` — ย้ายการจ้างจากบริษัทต้นทางไปบริษัทปลายทาง
- `SECONDMENT` — ไปช่วยงานชั่วคราวโดยยังรักษาการจ้างเดิม
- `DUAL_EMPLOYMENT` — มีการจ้างพร้อมกันมากกว่าหนึ่งบริษัท
เมื่อ Transfer เสร็จ:
1. ปิดหรือเปลี่ยนสถานะ Employee record บริษัทต้นทางตามวันที่มีผล
2. สร้าง Employee record บริษัทปลายทางใหม่
3. เชื่อมทั้งสองรายการกับ `person_id` เดียวกัน
4. เพิ่ม Employment history ของทั้งต้นทางและปลายทาง
5. กำหนด Company access ใหม่ให้ User
6. ไม่แก้ไข Payroll, Payslip, Leave และ Audit history เดิม
7. บันทึกทุกขั้นตอนด้วย Request ID เดียวกัน
### 9.19.5 สิทธิ์และ Company Context
ทุก Request ที่เข้าถึงข้อมูลบริษัทต้องผ่านเงื่อนไข:
1. User อยู่ใน Tenant เดียวกับ Company
2. มี `user_company_access.access_status = 'ACTIVE'`
3. Role และ Scope อนุญาตการกระทำนั้น
4. Object ที่ขออยู่ใน Company เดียวกับ Context
5. การกระทำระดับพนักงานผ่าน Department, Manager หรือ Self scope ตามสิทธิ์
ตัวอย่าง Query ตรวจ Company access:
```sql
SELECT 1
FROM user_company_access uca
JOIN organizations o
  ON o.id = uca.organization_id
WHERE uca.user_id = ?
  AND uca.organization_id = ?
  AND uca.access_status = 'ACTIVE'
  AND o.tenant_id = ?;
```
**ข้อกำหนด Backend**
- ดึง `tenant_id` จาก Session ที่ตรวจสอบแล้ว
- ดึง Company context จาก Route/Header แล้วตรวจ `user_company_access`
- Repository ทุกตัวต้องรับ Tenant ID และ Company ID อย่างชัดเจน
- Query ข้อมูลระดับบริษัทต้องมีทั้ง Tenant และ Company filter
- Background job ต้องบันทึก Tenant/Company context ใน Payload
- WebSocket channel ต้องแยกตาม Tenant และ Company
- Cache key ใช้รูปแบบ `tenant:{tenantId}:company:{companyId}:...`
- Storage path ใช้รูปแบบ `/{tenantId}/{companyId}/{module}/...`
### 9.19.6 Unique Constraint รายบริษัท
ข้อมูลต่อไปนี้ต้องไม่ซ้ำภายในบริษัท แต่สามารถซ้ำข้ามบริษัทได้:
- Employee number
- Branch code
- Department code
- Position code
- Job level code
- Work schedule code
- Leave type code
- Payroll cycle code
- Payslip number
ข้อมูลต่อไปนี้ต้องไม่ซ้ำภายใน Tenant:
- User email
- Tenant-level Role code
- National ID hash ของ `people` เมื่อมีค่า
- Company code
### 9.19.7 Payroll หลายบริษัท
- `payroll_cycles.organization_id` บังคับให้หนึ่งรอบเป็นของบริษัทเดียว
- `payroll_cycle_employees` รับเฉพาะ Employee ที่อยู่บริษัทเดียวกับรอบ
- Approval workflow และผู้อนุมัติต้องมี Company access
- สลิปและเลขเอกสารแยก Running number ต่อบริษัท
- รายงานรวมระดับ Tenant อ่านข้อมูลหลายบริษัทได้ แต่ไม่สร้าง Payroll cycle รวม
- รายงานรวมต้องแสดง Company code, Company name และ Currency
- ระบบปัจจุบันรองรับเฉพาะ THB แต่เก็บ Currency ที่ Company และ Payroll cycle เพื่อรองรับอนาคต
### 9.19.8 ประกาศหลายบริษัท
- `announcements.organization_id IS NULL` หมายถึงประกาศระดับ Tenant
- หากมี Company ID หมายถึงประกาศเฉพาะบริษัท
- ประกาศระดับ Tenant ต้อง Resolve ผู้รับจาก Company access ที่ผู้สร้างมีสิทธิ์
- Target ระดับ Branch/Department ต้องอยู่ภายใต้บริษัทเดียวกับประกาศ
- `announcement_user_activity` หนึ่งแถวต่อ Announcement/User ป้องกันการส่งซ้ำ
- รายงานต้องสามารถแยก Unique viewer และ Total view ตามบริษัท
### 9.19.9 Audit และ Data Isolation
ทุก Audit record ต้องตอบคำถามได้ว่า:
- เกิดใน Tenant ใด
- เกิดในบริษัทใด หรือเป็นเหตุการณ์ระดับ Tenant
- ใครเป็นผู้ดำเนินการ
- กระทบ Object และพนักงานใด
- ค่าเดิมและค่าใหม่คืออะไร
- เกิดจาก Request ใด
**Automated security tests ที่ต้องมี**
- User บริษัท A อ่าน Employee บริษัท B ไม่ได้
- Company Admin A เปลี่ยน Role ของ Company Admin B ไม่ได้
- Manager A เปิด Payroll หรือสลิปของบริษัท B ไม่ได้
- File URL ของบริษัท A ใช้ Session บริษัท B เปิดไม่ได้
- WebSocket/Notification ไม่ส่งเหตุการณ์ข้ามบริษัท
- Export รายงานรวมมีเฉพาะบริษัทที่ผู้ขอมีสิทธิ์
- การเปลี่ยน Company ID ใน URL หรือ Request body ต้องได้ 403
- Tenant หนึ่งไม่สามารถอ้าง ID ของอีก Tenant ได้ แม้เดา UUID ถูกต้อง
### 9.19.10 Index สำหรับ Multi-company
Version 3 เพิ่ม Index สำคัญ:
- `organizations(tenant_id, status)`
- `users(tenant_id, lower(email))`
- `people(tenant_id, national_id_hash)`
- `employees(person_id, organization_id)`
- `user_company_access(user_id, organization_id)`
- Partial unique index สำหรับบริษัทเริ่มต้นของ User
- `intercompany_employee_transfers(person_id, effective_date)`
Query ที่มีข้อมูลจำนวนมากควรเริ่ม Index ด้วย `tenant_id` หรือ `organization_id` ตามระดับของข้อมูล

## 9.21 สรุป Version 3
- จำนวนตารางเพิ่มจาก **60 เป็น 67 ตาราง**
- เพิ่ม Tenant เป็นขอบเขตสูงสุดของระบบ
- เปลี่ยน Organization ให้หมายถึงบริษัทหรือนิติบุคคล
- เพิ่มข้อมูลบุคคลส่วนกลางและการจ้างงานแยกตามบริษัท
- เพิ่ม Company access และ Role scope รายบริษัท
- เพิ่ม Workflow การย้าย ยืมตัว และทำงานหลายบริษัท
- รองรับประกาศ รายงาน Export และ Audit ระดับ Tenant
- ไฟล์ปัจจุบันคือ `hrm-sqlite-schema-v3-multicompany.txt`
- Migration version คือ `003_multi_company_schema`
- ผ่านการทดสอบสร้างฐานข้อมูลด้วย SQLite และเปิด Foreign key แล้ว
## 9.22 แนวทาง Migration จาก Version 2
ไฟล์ Version 3 เป็น **Baseline Schema สำหรับฐานข้อมูลใหม่** ไม่ควรรันทับฐานข้อมูล Version 2 โดยตรง
ลำดับ Migration สำหรับระบบที่มีข้อมูลแล้ว:
1. สำรองฐานข้อมูลและหยุดงานเขียนข้อมูล
2. สร้าง `tenants` และ Tenant เริ่มต้น
3. เพิ่มและ Backfill `organizations.tenant_id`
4. สร้าง `people` และเชื่อม Employee เดิมด้วย `person_id`
5. Rebuild `users` ให้ย้ายจาก Company scope ไป Tenant scope
6. สร้าง `user_company_access` จาก Company เดิมของ User
7. Rebuild `roles` และ `user_roles` ให้รองรับ Tenant/Company scope
8. เพิ่ม Tenant context ให้ Announcement, Notification, File, Audit และ Export
9. สร้างตาราง Multi-company ใหม่ที่เหลือ
10. ตรวจ Orphan, Duplicate และ Cross-tenant reference
11. รัน `PRAGMA foreign_key_check`
12. ทดสอบ Permission และ Cross-company data leakage
13. บันทึก Migration version เมื่อทุกขั้นตอนสำเร็จ
> SQLite อาจต้อง Rebuild ตารางสำหรับการเปลี่ยน Foreign key, NOT NULL หรือ Primary key ห้ามใช้คำสั่ง ALTER แบบสมมติว่าเทียบเท่า PostgreSQL
